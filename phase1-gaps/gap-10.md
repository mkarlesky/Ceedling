# GAP-10 report: path language in the docs the promise ledger did not cover

## Summary

I ledgered 61 path promises and findings from the user docs and plugin docs that stream 5 left out. The headline experiment answers the `_AT` question. Two same-named modules `a/util` and `b/util` in one test do not collide on the generated names that drop the directory, unless they already collide on a name the module owns. Type names such as `ceedling_partial_util_s_ctx_t` repeat across the two modules. They clash at compile time only when both modules declare a variable of the same name, and that variable already clashes at link without the type. Generated files, include guards and mock lifecycle names keep the directory and stay apart. 
The ledger found these promises broken: a Partial module named like a predefined macro such as `unix` never reaches its file, the tasks `paths:header` and `files:include` do not exist, `files:assembly` exists with assembly off, a release build needs `:paths ↳ :test`, and the Dependencies plugin's `:artifact` path skips `:source` and its clean misses the default path. 
`test:path` is a substring match on the test's directory only, not on its path. Most other path promises hold. The generated Partial headers hold bare-name includes that are right only because the compiler checks the includer's directory first. 
Final status after verification: 53 confirmed, 8 revised. No gcov, Bullseye or Cppcheck run happened, so those rows rest on reading the plugin code.

## The same-named `_AT` experiment

One test file holds two `#include TEST_PARTIAL_*_MODULE_AT` lines, one for `a`, one for `b`, both naming `util`. Each `util.c` defines a static and a public function. Names inside the projects are in `collide/gen.sh`.

| v5 | PUBLIC ×2; `a_ctx`, `b_ctx` typed statics | builds, 1 passed | `ceedling_partial_util_a_ctx_t`, `..._b_ctx_t` differ |

The generated identifiers in the passing build are these. Files sit below `build/test/partials/test/test_collide/_t_/`.

- Files: `a/ceedling_partial_util_impl.{c,h}` and `b/ceedling_partial_util_impl.{c,h}`.
- Include guards: `GENB59956D4_A_CEEDLING_PARTIAL_UTIL_IMPL_H_CEEDLING` and `GEN7118F419_B_CEEDLING_PARTIAL_UTIL_IMPL_H_CEEDLING`.
- Type names (v4): `ceedling_partial_util_s_ctx_t` in both types headers.
- Mock names (v6): `a_Mockceedling_partial_util_interface_Init` and `b_Mockceedling_partial_util_interface_Init`.
- Promoted statics: `partial_<function>_<variable>`, with no module part.

The answer to the question is no, with one qualification. The module name without its directory appears only in type names. A type name repeats across the two modules only when the variable's name repeats, and then the variable collides by itself. Nothing else tested collides on the module name alone. The qualification is that `PARTIAL_TYPE(util, s_ctx)` cannot say which module it means. That matters only to a design that wants both modules' variables of one name in one test, and the variable name would still have to differ.

## Defects and open questions

### Defects

- **GAP10-08** A Partial module name that is a predefined macro is replaced before it names the file. In a GCC build the compiler predefines `unix` as 1. A test with `#include TEST_PARTIAL_PUBLIC_MODULE(unix)` and a `unix.c` module preprocesses to `#include "ceedling_partial_1_impl.h"`. Ceedling reads the directive as written and generates `ceedling_partial_unix_impl.{c,h}`. It also writes an empty `ceedling_partial_1_impl.h`. The test links without the module and fails with `undefined reference to 'unix_pub'`, under a notice that blames missing `#include` lines. `__PARTIALS_EXPAND(module)` expands the argument, and `_validate_module!` checks only for an empty, quoted or path-bearing name. The `_AT` module argument passes through `__PARTIALS_JOIN`, whose indirection also expands macros. That path was inferred and not built.
- **GAP10-20** ceedling paths:header does not exist; the task is paths:include. The reference lists `ceedling paths:header`. Ceedling defines a `paths:<name>` task for each key of `:paths`, and the standard sections are test, source, include and support. `ceedling paths:header` ends with `Unrecognized build task`. `paths:include` lists the include paths. The getting-started page repeats the error by listing `files:*` variants under `paths:*`.
- **GAP10-21** files:assembly exists even when assembly support is off. Both command line pages say the task is only available when assembly support is enabled. The `files` namespace creates a task for each of tests, source, assembly, headers and support unconditionally. With `:test_build` ↳ `:use_assembly: FALSE` and no release assembly, `ceedling files:assembly` runs and prints `Assembly files: None`.
- **GAP10-22** The Dependencies doc names a files:include task that does not exist. The doc lists `files:include` as "Lists every header file Ceedling has found, including those from dependencies". The core defines `files:header` for that. `ceedling files:include` ends with `Unrecognized build task`. `paths:include` is real.
- **GAP10-23** Dependency include directories and globs are added to the header file collection as literal entries. `include_files` maps every `:includes` entry, whether a header, a directory or a glob, to a path below the artifact path. `Dependencies#config` and `#add_headers_and_sources` push all of them into `collection_all_headers`. With `:includes: [inc/**, single/one.h]`, `files:header` lists `dependencies/Vend/inc/**` as a header file.
- **GAP10-24** A dependency's :artifact path skips :source and :fetch when :build is left out. The docs say `:artifact` falls back to `:build`, and `:build` falls back to `:source`, then `:fetch`. The code reads `@paths[:artifact] || @paths[:build] || default_path`. A dependency with only `:source: ext/src` gets build `ext/src` but artifact `dependencies/<name>`. In the build, `:includes: [inc/**]` of such a dependency appears in `paths:include` as `dependencies/Vend/inc`, not `vendor_dep/inc`. A fix changes where artifacts are looked for, so it is a BreakingChanges candidate.
- **GAP10-38** A release build needs :paths :test although the project file docs list only :build_root and :paths :source. A project with `:release_build: TRUE`, `:project` ↳ `:build_root` and `:paths` ↳ `:source`, and no `:paths` ↳ `:test`, stops with `Required config file entry :paths ↳ :test does not exist.` The check lists `:paths` ↳ `:test` for every build.
- **GAP10-45** The release-build doc example names build/release/out/c/, which the layout does not use. The `:artifacts` example is `build/release/out/c/top_secret.s19`. Release objects sit at `build/release/out/<source directory>/<name>.o` (`build/release/out/src/main.o`, `.../src/drv/led.o`). No `c/` directory exists.
- **GAP10-49** The tools doc's compile and link examples show a layout Ceedling does not build. The example compile line has `-I"project/tests" -I"project/source"` and outputs `build/tests/out/source.o`. The linker example writes `build\tests\out\test_thing.exe`. Ceedling builds objects at `build/test/out/<test path>/_t_/<mirrored file path>.o` and links `build/test/out/<test path>/_t_/<test>.out`. Source directories are not `-I` entries, and a test directory is one only when it holds a header.

### Open questions

- The runner of a test naming two same-named `_AT` Partials includes one impl header by bare name (GAP10-10). I did not trace which step collapses the two.
- Windows behavior of mixin names and `~` in `:which_ceedling` (GAP10-34, GAP10-40). Traced from code only. No Windows run, and no `~` run for which-ceedling.
- Whether `_AT`'s module argument is macro-replaced the way the unqualified argument is (GAP10-08). The code path suggests it. I did not build it.
- Bullseye's claim that stored source paths are relative to the coverage file, and every gcov, gcovr and ReportGenerator row. No tool ran.
- GAP-04 overlap. I left out the Dependencies `:includes` directory rule and `:build_lib` object placement, and Bullseye's coverage filters, as the brief says.

### Doc rows that matter for a redesign

- The generated Partial headers and sources depend on the includer's directory for their own bare-name includes (GAP10-09). Any resolver that skips the includer breaks them when two same-named Partials share the `-I` list.
- `test:path` selects by directory substring (GAP10-16). A rewrite that matches path components is a BreakingChanges entry.
- The Dependencies plugin's path fallbacks (GAP10-24, GAP10-25) disagree with its docs in ways that depend on which paths a project names.
